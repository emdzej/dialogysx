# The imported tree

`data-format.md` describes the discs. This describes what an importer _builds_
from them, and what a reader may assume about it.

This is the one format here that is not Renault's. It exists because the discs
are not directly usable: there are five of them, they overlap, their version
stamps disagree, and the paths a reader needs are spread across all five. An
imported tree is one directory that answers every read, and it carries two
manifests describing itself.

Section numbers in `§n` form refer to `data-format.md`.

## 1. Layout

Directory names are the discs' own, preserved deliberately — every path
reference inside the data is relative to these, so renaming them would mean
rewriting the data.

```
data/
├── manifest.json          what the tree contains, and where it came from  (§2)
├── csfs-manifest.json     every path and its size, for HTTP readers       (§3)
│
├── pr/                    plates, assemblies, part-number index, models
│   ├── Planches.dat/.idx  the parts layer (§3.1)
│   ├── Organes.dat/.idx   the assembly layer (§3.2)
│   ├── refNumPr…          part number → PR groups (§3.3)
│   ├── ListePRModele      model names
│   ├── FamilleModeleAll.dat   model → documentation family (§5)
│   ├── ListeDoc<Brand>    brands
│   └── <group>.zip        per-group criteria value tables (§3.8)
├── enveloppe/             the vehicle list (§3.5)
├── Dates/                 applicability dates (§3, resolution.md §4)
├── langue/<lg>/           classicvar.utf, menu, papv (§3.7)
├── tarif/d3k/<CC>/<lg>/   part descriptions, per country
├── PR1100/                part substitutions
│
├── dessins/100.zip        38,488 parts drawings, kept packed
├── eclate/100.zip         exploded views
├── vignette/{pr,tm,…}/    thumbnails, per menu entry
│
└── mrnt/<lg>/             repair documentation (§5)
    ├── indexation/        the document indexes
    ├── 1-MR/, 1-NT/       the PDFs
    └── d3k/images/<n>/    illustration archives, kept packed, one dir per disc
```

Sizes from a real English 4.55 import: **43,915 files, 15.30 GB**, of which
`mrnt/` is 43,273 files and 14 GB.

## 2. `manifest.json`

What the tree contains and where it came from. Written **last**, so a failed or
abandoned import leaves a tree with no manifest rather than one that looks
complete.

```json
{
  "manifestVersion": 1,
  "builtAt": "2026-09-04T15:14:04.349Z",
  "sources": [
    {
      "kind": "catalogue",
      "label": "parts catalogue",
      "root": "/Volumes/dialogysDVD1 1",
      "versions": { "VersionData": "versmpf=4.5.5" }
    },
    {
      "kind": "mrnt",
      "label": "repair documentation: en (1-MR, 1-NT, images, indexation)",
      "root": "/Volumes/CDROM 3",
      "versions": { "VersionData": "versmpf=4.55.20160819" }
    }
  ],
  "catalogueLanguages": ["en"],
  "repairLanguages": ["en"],
  "datasets": [{ "id": "planches", "keyLength": 11, "depth": 2, "keys": 40910 }],
  "counts": { "files": 43421, "extractedEntries": 494, "bytes": 15300208239 },
  "archives": [{ "archive": "/dessins/100.zip", "serves": "/dessins/100", "entry": "basename" }]
}
```

**Why the version stamps live here and not in the tree.** They genuinely
disagree between discs — the catalogue says `versmpf=4.5.5`, the repair discs
say `versmpf=4.55.20160819` — and merging them into one path would mean picking
a winner. Recording them per source keeps both facts.

**Why the dataset key counts are here.** A reader can tell whether a tree is
complete without opening it, and an importer that wrote a truncated index is
caught by comparing. They are probed from the _result_, not taken from the
plan, so a resumed or partial import is described accurately rather than
optimistically.

**`catalogueLanguages` and `repairLanguages` are separate.** A tree can carry
`langue/en/` without `mrnt/en/`, and does whenever the repair discs were not
imported. They are also both distinct from the _interface_ language, which is
not a property of the tree at all.

## 3. `csfs-manifest.json`

**HTTP cannot list a directory.** A static host serves any file you name and
tells you nothing about what is there, so a tree meant to be read over HTTP
carries a flat map of every path to its size:

```json
{
  "csfs": 1,
  "label": "dialogysx parts catalogue + repair documentation: en",
  "builtAt": "2026-09-04T…",
  "files": { "/pr/Planches.dat": 4194304, "/dessins/100.zip": 670089677 },
  "archives": [{ "archive": "/dessins/100.zip", "serves": "/dessins/100", "entry": "basename" }]
}
```

The format is `@emdzej/csfs-manifest`'s, not ours, and it is generated by
csfs's own builder rather than reimplemented — so a change to the format is
followed instead of quietly duplicated.

Flat rather than nested for three reasons: a lookup is one map hit instead of a
fetch per directory level; paths in a real tree share long prefixes and
compress well; and directories can be _derived_ from the paths, which is what
lets an archive stand in for a directory that is not on disk.

Measured: **43,915 entries describing 15.30 GB come to 4.02 MB of JSON, 0.42 MB
gzipped** — 9.4:1, paid once when the tree is opened. Extracting the archives
serves the same bytes from 228,515 paths and the manifest grows to 14.72 MB. A
manifest is priced in paths, not bytes, which is the whole argument for §4.

**Neither manifest lists itself.** `csfs-manifest.json` cannot — its size would
depend on its contents, which does not settle. `manifest.json` _is_ listed, and
leaving it out was a real bug: when csfs is the file system, an unlisted file is
simply absent, so the archive mounts and the language list silently became
empty and the catalogue fell back to part codes.

## 4. Archives kept packed

Nine vendor archives are copied verbatim rather than extracted, and the
manifests declare which directory each stands in for:

```json
{ "archive": "/dessins/100.zip",              "serves": "/dessins/100",        "entry": "basename" }
{ "archive": "/mrnt/en/d3k/images/3/images_1.zip", "serves": "/mrnt/en/d3k/images", "entry": "basename" }
```

This removes **184,610 files for the same bytes** — 43,915 instead of 228,515.
It matters more than it sounds: on macOS with endpoint security active, file
creation ran at roughly 5 files/second while streaming ran at 58–109 MB/s, so
the extracted import was bounded by file _count_, not size.

Three things about a mount:

- **`entry: "basename"` is a fact about the archive, not a default.**
  `dessins/100.zip` stores drawings flat as `1132C000.png`, while every
  reference in the data says `dessins/100/1132/1132C000.png`. The archive and
  the extracted layout are _different shapes_, and only the tree's author knows
  how one maps onto the other.
- **Several archives can serve one directory.** Three of the English discs each
  ship an `images_1.zip` with different contents, so each is copied into a
  per-disc subdirectory and all of them mount over `mrnt/<lg>/d3k/images`.
  Their entry names do not overlap — measured, 0 of 36,374 on the Russian set —
  so the order does not matter.
- **A real file wins.** A tree that _was_ extracted keeps working, and a
  half-extracted one falls back file by file.

Mount paths are `/`-rooted in both manifests, which is the same shape
`@emdzej/csfs-zip` takes for a mount, so the array is handed over unchanged.

## 5. Components

An import is selectable, because the full set is 15 GB and most of it is
optional. `dialogysx import --list-components` is authoritative; the shape is:

|     | component              | without it                                              |
| --- | ---------------------- | ------------------------------------------------------- |
| !   | `parts`                | nothing works — this is the catalogue                   |
| *   | `criteria`             | criteria show as raw codes and cannot be evaluated      |
| *   | `drawings`             | no plate illustrations; the parts list still works      |
| *   | `exploded`             | no exploded views or thumbnails                         |
| *   | `dates`                | no date-based applicability (resolution.md §4)          |
| *   | `substitutions`        | no "replaced by" lookups                                |
| *   | `part-names`           | bare 10-digit references and no descriptions            |
| *   | `repair`, `repair-pdf` | no documentation                                        |
|     | `drawings-extracted`   | nothing — `drawings` serves the same images             |
|     | `labour-times`         | no repair-time figures                                  |
|     | `pricing`              | no prices — **out of scope by decision**                |
|     | `extras`               | nothing yet — none of it is decoded                     |
|     | `app`                  | nothing at run time; reverse-engineering reference only |

`!` is always included. `pricing` and `labour-times` are named rather than
silently dropped, so their absence reads as a decision.

**Unclaimed files are reported, not copied.** Anything matching no component is
listed at the end of a plan. That is how `TM.zip`, `tarif.zip` and `REACH.zip`
were found in the first place, and it is why a new disc revision cannot quietly
add data nobody notices.

## 6. A copy in the browser

The same tree can be held in a browser's own storage (OPFS), copied from
whichever source is open. It is a byte copy with the same layout and the same
two manifests, so nothing about the format changes — but it is worth knowing
why anyone would:

**It never prompts.** A picked directory comes back after a reload and its
permission does not, so an app that wants to open and just work cannot rely on
one. OPFS has no such gate, which is what makes "installed, no network, no
clicks" reachable at all.

Three properties a reader should know about that copy:

- **The browser decides how large it may be**, and the limit is routinely
  smaller than a full tree — measured at 7.52 GB granted on a machine with far
  more free disk, against 15.30 GB of data. So a copy is often a _subset_, and
  the catalogue without `mrnt/` is 0.85 GB precisely because that subset is the
  useful one.
- **It is evictable** unless `navigator.storage.persist()` has been granted.
- **`csfs-manifest.json` travels with it**, so the copy describes itself and a
  partial copy can be resumed by comparing sizes. Its claims are re-checked
  against what is actually stored rather than trusted: a cancelled copy leaves
  the manifest naming files it never wrote.

The enumeration for such a copy comes from that manifest rather than from
walking, for the same reason it exists in the first place — a source reached
over HTTP cannot list a directory.

## 7. Resume, and what a reader may assume

An import is resumable: `.dialogysx-import.json` in the target records
destination path → size written, so a second run skips what is already there
and reports anything whose size differs as a conflict rather than overwriting
it.

A reader may assume:

- every path in `csfs-manifest.json` exists and has that size;
- every archive in `archives` exists and can be read by byte range;
- `pr/` is complete if `manifest.json` lists the `planches` and `organes`
  datasets with their key counts;
- nothing else. Any directory may be absent, and the reader's job is to degrade
  — codes instead of names, no drawing, no documentation tab — rather than to
  fail.

The one thing a reader may _not_ assume is that a tree with no
`csfs-manifest.json` is broken. It is only unreadable over HTTP;
a directory handle or `node:fs` can list for itself. `dialogysx manifest <tree>`
writes one for a tree that predates it.
